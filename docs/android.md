# Hall-e for Android

The Android companion is an agenda, reminder, and optional local recording app. Candidate 0.3.0/code 4 uses the Órbita Imba interface compiled into local app assets and exposed to native Android capabilities through a bridge. The initial local recording action is available before project selection. Hall-e's preview mode (`HALLE_PREVIEW`) uses synthetic sample interactions and does not invoke the native bridge or record audio; verify microphone behavior with the installed Android app.

The agenda reads selected calendars through Android's `CalendarContract` and provides month and week views. Users can organize meetings into local projects, keep or share Markdown notes, and move meetings to trash with restore. Trash preserves source calendar events and hides their Hall-e reminders while trashed. Projects, assignments, notes, recordings, preferences, and reminder identifiers are stored on the phone. Pairing shares selected client-encrypted meeting details plus coordination metadata through the Hall-e coordinator with paired Hall-e devices, including Mac. Hall-e has no account system.

## Requirements and build

- Android Studio / Android Gradle Plugin 9.0.0, Gradle 9.1.0, and JDK 17.
- Android SDK Platform 36 (the app's minimum supported Android version is API 31).
- Build the local Imba assets first: from `android/mobile-ui`, run `npm ci` and `npm run build`. Then, from `android`, run `./gradlew assembleDebug` (and `./gradlew test` for local JVM tests). The Gradle bootstrap downloads the pinned Gradle 9.1.0 distribution and verifies its SHA-256 before use. Android Studio can open the `android` directory directly. These are local build commands; they do not claim hosted verification or a production release.
- The local Imba preview is not a substitute for checking native recording on an Android device. This candidate's native instrumentation regression is `app/src/androidTest/java/app/halle/companion/MobileStoreInstrumentation.kt`.
- The SDK path may be supplied through `ANDROID_HOME` or `ANDROID_SDK_ROOT`, or configured locally by Android Studio. `local.properties` is ignored.
- For a signed release, set `ANDROID_KEYSTORE`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, and `ANDROID_KEY_PASSWORD`. A release task fails if any value is missing. Keep keystores and passwords out of source control.

## Calendar access and reminders

Hall-e requests read-only calendar permission at runtime. It initially selects the calendars available on the device; the user can change that selection in Settings. It reads occurrences from `CalendarContract.Instances`, and excludes canceled or declined events. All-day entries appear in the agenda but do not trigger alerts. Occurrence identifiers include the calendar, event, and start time so recurring meetings can be scheduled separately. Changes to device time, timezone, date, boot state, or calendar provider request a reminder refresh. The app schedules the next 30 days of upcoming reminders and refreshes them when opened.

Reminder timing can be set to meeting start, 1, 5, 10, 15, or 30 minutes before, or a custom interval from 1 to 1440 minutes. Android notification permission and exact-alarm access are controlled by the operating system and may be denied or revoked. Without notification permission no notification is shown; without exact-alarm access Android may deliver a reminder later than requested, subject to system power restrictions. The app does not use a persistent foreground service to promise delivery.

The morning overview is shown on the first app open from 04:00 until noon local time on a given date, if calendar access is available and the feature is enabled. It is not a guaranteed background notification: Android may not start the app before the user unlocks or opens it, especially after a reboot. The overview is generated only when the app opens during that local-time window.

## Privacy

The app requests calendar read, notifications, exact alarms, boot-completed, microphone, foreground microphone service, and network permissions. It does not request calendar write access, contacts, or location. Calendar data, event IDs, and notes remain local; sharing a note is an explicit Android share-sheet action. Meeting URLs are limited to recognized conferencing hosts and open in an external app or browser.

Android recording is optional and starts only after a visible user action and microphone permission. New recordings stay in app-private storage and are eligible for phone-to-Mac transfer only after recording stops. The phone encrypts audio chunks for the registered Mac device and queues the transfer for retry through Android's OS job scheduler. The coordinator stores and relays ciphertext and transfer metadata; it cannot read audio, transcript content, calendar contents, or encryption keys. The Mac writes the transcript durably, purges its received audio, and returns a signed receipt. After validating the receipt, the phone durably stores it, purges its audio, and sends a relay acknowledgement. Historical recordings without explicit enrollment in this transfer flow are not automatically purged. Without pairing, meeting details and recordings stay on that phone.

If the user explicitly creates or joins a shared workspace, Hall-e encrypts a meeting title and optional project name, meeting URL, and scheduled times on the device before sending them to the allowlisted coordinator. The coordinator also stores opaque workspace/device/session IDs, display-only device names, session ciphertext, audio-transfer ciphertext and metadata, segment timestamps/status, and recording-lease metadata. It does not receive the calendar event ID, calendar contents, or encryption key. Credentials and the workspace key are encrypted with an Android Keystore key.

Shared live recording remains exclusive across the workspace. A phone must publish the encrypted session and obtain a short-lived lease before it starts its microphone; it renews while recording and stops locally if renewal fails or another device requests handoff. The separate live-session lease handoff is only a prompt to the current phone. It cannot start recording on the target phone. The target user must separately choose to record and grant microphone access. Post-stop phone-to-Mac audio transfer uses the registered-device queue and does not replace or alter that shared live-recording handoff.
